## 1. Цель работы

Реализовать на сервере ASP.NET Core (`http://localhost:5000`) маршруты главного объекта (`Orders` — заказы на контроллеры) с хранением в оперативной памяти: создание (`POST /api/orders` → `201`), чтение списка (`GET /api/orders` → `200`, включая `[]`), чтение одной записи (`GET /api/orders/{id}` → `200` / `404`), отдельное назначение исполнителя (`PATCH /api/orders/{id}/assignee`) и отдельную смену статуса (`PATCH /api/orders/{id}/status` → `200` / `409`); настроить безопасное логирование сбоев без выдачи `stack trace` клиенту и подготовить коллекцию Postman.

## 2. Таблица маршрутов и кодов ответа

| Метод и путь                          | Успех         | Отказ              | Назначение и правила |
| ------------------------------------- | ------------- | ------------------ | -------------------- |
| `POST /api/orders`                    | `201 Created` | `400`, `500`       | Создаёт заказ. Принимает только `title` (5–80 символов), `modelId` (> 0), `description` (10–500 символов). Сервер сам задаёт `id`, `number` (`ЗК-2026-0003`), `status: "New"`, `assigneeUserId: null`. |
| `GET /api/orders`                     | `200 OK`      | `500`              | Возвращает список заказов; если пуст — `200` и `[]`. |
| `GET /api/orders/{id}`                | `200 OK`      | `404`              | Возвращает один заказ или `404 Not Found`. |
| `PATCH /api/orders/{id}/assignee`     | `200 OK`      | `400`, `404`, `409`| Отдельно назначает исполнителя (`{ "assigneeUserId": 5 }`, целое число > 0). Для завершённого заказа — `409`. |
| `PATCH /api/orders/{id}/status`       | `200 OK`      | `400`, `404`, `409`| Отдельно меняет статус (`New`, `InProgress`, `Closed`, `Cancelled`). Недопустимый переход или `InProgress` без исполнителя — **`409 Conflict`**. |

Метод `DELETE` не используется: отмена заказа — статус `Cancelled`. Маршруты также доступны по псевдониму `/api/tickets` (имя из методички).

## 3. Обязательные запросы из коллекции

Коллекция лежит в `docs/api-collection/orders.postman_collection.json` (копия под стандартным именем — `tickets.postman_collection.json`).

1. **Успешный `POST /api/orders`** с телом `{"title": "Контроллеры для линии упаковки", "modelId": 2, "description": "6 шт., интерфейс Modbus TCP, исполнение для работы при температуре до +70 °C"}` → **`201 Created`**, в теле `id`, `number` (`ЗК-2026-0003`), `"status": "New"`, `"assigneeUserId": null`.
2. **`POST` с коротким `title` из 3 символов (`"Абв"`)** → **`400 Bad Request`** (`ValidationProblemDetails`: поле `title` должно содержать от 5 до 80 символов).
3. **`GET /api/orders/999999`** → **`404 Not Found`** (`ProblemDetails`: заказ с `id=999999` не существует).
4. **`PATCH /api/orders/1/status`** с `{"status": "InProgress"}` без назначенного исполнителя → **`409 Conflict`** (нельзя перевести заказ в `InProgress`, пока не назначен исполнитель).
5. **Оба `PATCH` по порядку.** Сначала `PATCH /api/orders/1/assignee` с `{"assigneeUserId": 5}` → **`200 OK`**; затем `PATCH /api/orders/1/status` с `{"status": "InProgress"}` → **`200 OK`**.

## 4. Лог неожиданной ошибки и безопасный ответ 500

Если после проверки полей в `OrdersController.Create` временно раскомментировать учебное исключение `throw new InvalidOperationException("Simulated unexpected failure after validation")`:

1. **Строка в логе сервера (терминал `dotnet run`):**
   ```text
   fail: backend.Controllers.OrdersController[0]
         CreateOrder failed; modelId=2; error=InvalidOperationException
   ```
2. **Ответ клиенту (`500 Internal Server Error`, `application/problem+json`):**
   ```json
   {
     "type": "https://tools.ietf.org/html/rfc9110#section-15.6.1",
     "title": "Сервер не смог обработать запрос",
     "status": 500,
     "detail": "Неожиданный сбой при создании записи."
   }
   ```
   В ответе нет `stack trace`, путей файловой системы, тела запроса и секретов. Перед коммитом учебный сбой снова закомментирован.

## 6. Ответы на вопросы для устной защиты

### 1. Почему назначение исполнителя и смена статуса — два отдельных `PATCH`?
Это две разные бизнес-операции с разными входными данными и правилами. Исполнителя назначает начальник участка, а в производство и в отгрузку заказ переводит назначенный инженер. Два узких маршрута делают API предсказуемым и не позволяют случайно перезаписать чужие поля.

### 2. Чем код `400` отличается от `409`?
`400 Bad Request` — сам запрос некорректен по форме или значениям (невалидный JSON, наименование короче 5 символов, `modelId <= 0`, неизвестный статус); его нельзя выполнить ни при каком состоянии записи. `409 Conflict` — запрос корректен (`"status": "InProgress"` — допустимый статус), но противоречит текущему состоянию заказа (исполнитель ещё не назначен, или переход из текущего статуса недопустим).

### 3. Почему пустой список возвращает `200`, а не `404`?
`GET /api/orders` обращается к коллекции: маршрут и коллекция существуют, в ней просто ноль элементов. Поэтому `200 OK` и `[]`. `404` возвращается, только когда запрошена конкретная запись по `id`, которой нет.

### 4. Что видит клиент и что видит разработчик при неожиданном сбое?
Клиент получает безопасный `ProblemDetails` с кодом `500` и общим сообщением без `stack trace` и внутренних путей. Разработчик видит в серверном логе одну строку (`CreateOrder failed; modelId=2; error=InvalidOperationException`), по которой понятно, какая операция, с какими параметрами и с каким типом исключения завершилась сбоем.
